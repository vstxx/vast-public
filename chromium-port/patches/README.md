# Chromium patch series

`series.json` defines patch order. The first patch establishes the reproducible Vast product identity while retaining open Chromium behavior.

Each entry has this form:

```json
{
  "file": "0001-vast-product-foundation.patch",
  "description": "Add the minimal Vast product foundation"
}
```

Generate patches from the pinned Chromium checkout with binary changes included. Never include build output, credentials, profiles, cookies, or generated user data.

`0001-vast-product-foundation.patch` adds the Vast product name, a dedicated Windows application identity, ProgIDs, protocol scheme, COM class IDs, and sandbox SID namespace. It deliberately keeps Chromium behavior and assets instead of enabling proprietary Google Chrome branding.

`0002-rebaseline-public-sdk-midl.patch` records the two deterministic x64 TLB outputs generated by the pinned public Windows SDK.

`0003-vast-windows-icon.patch` adds the Vast multi-resolution Windows icon and selects it only when `VAST_BRANDING` is enabled. Chromium and Google Chrome branding branches remain intact.

`0004-vast-webui-foundation.patch` registers `chrome://vast`, adds its profile-scoped C++ controller, allocates a GRIT resource range, and bundles the first TypeScript/CSS/HTML product surface without a localhost server.

`0005-vast-mojo-runtime-info.patch` upgrades that surface to `MojoWebUIController`, registers a URL-scoped `PageHandlerFactory`, and returns native runtime facts through generated C++ and TypeScript bindings. It is the first tested renderer-to-browser service boundary for Vast.

`0006-vast-data-migration-preview.patch` adds the first native data-compatibility component. It reads copied fixtures on a `MayBlock` ThreadPool task, enforces the Electron schema size/collection limits, returns only aggregate counts, detects but never reads the password vault, and rejects malformed JSON through the same Mojo boundary.

`0007-vast-data-root-resolution.patch` adds the Electron `data-root.json` contract to that native component. It accepts only bounded JSON with an absolute `customDataRoot`, falls back to the stable config root when no override exists, and never returns the resolved path to WebUI.

`0008-vast-data-migration-unittests.patch` adds the first native Vast-specific Chromium test executable. Its five tests cover default and custom roots, vault metadata exclusion, malformed input, relative-root rejection, and the 8 MiB bound without reading or modifying production data.

`0009-vast-data-migration-transaction.patch` adds the native copy-first transaction. It copies only an explicit Vast product-data allowlist, rejects links/junctions and bounded-size violations, creates a separate safety backup plus verified staging tree, records per-file SHA-256 values, atomically promotes a new destination, and rolls back by moving data into a holding directory rather than deleting it. Electron cookies, sessions, `Local State`, and other browser-profile state are excluded.

`0010-vast-migration-transaction-webui.patch` adds an opt-in development-fixture control path to `chrome://vast`. Renderer code supplies no filesystem paths: the browser process reads pre-authorized command-line fixture/transaction roots, uses a fixed destination name, requires explicit UI confirmation, returns only non-sensitive state/counts over Mojo, and offers tested rollback. Without the dedicated enable switch, all write operations stay disabled.

`0011-vast-backup-v1-extractor.patch` implements the Electron 1.0.11 `.vastbackup` v1 boundary natively. It validates the bounded ZIP envelope and local/central entries, rejects unsafe/colliding Windows paths, encryption, unsupported compression, zip bombs, undeclared files, size drift, CRC errors, and SHA-256 mismatch. Every manifest file is streamed and verified, but only the explicit Vast product-data allowlist is written; the synthetic archive test feeds that output through prepare, commit, and rollback.

`0012-vast-native-backup-audit-tool.patch` adds the test-only `vast_backup_audit` executable. It invokes the exact native extractor against a pre-authorized archive, prints aggregate JSON only, removes its extracted product-data directory before exit, and fails if cleanup fails. It never selects an active data root.

`0013-vast-backup-fixture-webui-transaction.patch` lets development `chrome://vast` select exactly one native source: a copied data-root fixture or a pre-authorized `.vastbackup`. Archive preview verifies and deletes a temporary extraction; commit verifies again to prevent preview/commit substitution, prepares the existing copy-first transaction, deletes extraction before promotion, and exposes only aggregate counts through Mojo. The real supplied backup passed preview, commit, and rollback.

`0014-vast-workspace-settings-projection.patch` adds the first typed, read-only projection of migrated product state. It validates unique workspace IDs, the active workspace, bounded presentation fields, ordering/privacy metadata, and a strict appearance/layout settings subset with safe defaults. It deliberately omits tabs, URLs, history, notes, credentials, vault contents, and all browser-profile data; four additional native tests bring the data suite to 18/18.

`0015-vast-product-data-root-recovery.patch` adds native-only activation and restart recovery for a committed Vast 2 product root. A small record lives below the disposable Chromium profile, but recovery trusts neither that record nor paths alone: it revalidates the committed v1 transaction journal, path relationships, allowlist, file limits, SHA-256 for both active data and safety backup, and the typed schema projection. Rollback moves the committed data first and only then clears selection metadata. Four tests bring the native suite to 22/22; WebUI wiring remains a separate patch.

`0016-vast-product-root-webui-restart.patch` connects activation and recovery to the development `chrome://vast` transaction through typed, pathless Mojo. The renderer receives only the safe workspace/settings projection; paths, checksums, tabs, URLs, history, notes, and secrets remain native. Commit activates the root below the disposable profile, a new browser process revalidates and displays it, and rollback can recover its transaction from disk before moving data and clearing selection. Both the synthetic fixture and supplied real backup pass this process-restart flow.

`0017-vast-profile-keyed-data-service.patch` moves the recovered snapshot from individual WebUI controllers into `VastProductDataService`, owned once per regular Chromium profile. It coalesces asynchronous recovery, caches one validated snapshot, and supports explicit invalidation after commit/rollback. Its factory is registered during `ChromeBrowserMainExtraPartsProfiles::PreProfileInit`; lazy construction at first `chrome://vast` navigation is forbidden by Chromium's complete dependency-graph invariant and was caught by a `DependencyManager::AddComponent` CHECK during smoke testing. Two service tests bring the native suite to 24/24.

`0018-vast-native-shell-new-tab.patch` is the first visible Vast Shell milestone. Regular-profile `chrome://newtab` is rewritten through Chromium's existing NTP machinery to the profile-scoped `chrome://vast` controller, while incognito/guest behavior remains upstream. A final Vast color mixer gives the native frame, tab strip, toolbar, omnibox, bookmark bar, and NTP tokens the established dark/cyan palette without overriding Windows high-contrast or explicit custom themes. The WebUI becomes a product dashboard with search, Chromium destinations, workspace rail, safe appearance/session chips, and the existing development migration controls. A small dedicated test executable verifies the exact shell palette and the high-contrast escape hatch.

`0019-vast-native-workspace-toolbar.patch` adds the first persistent Vast-owned control outside page content. A native Chromium Views chip is present in regular-profile browser toolbars on every ordinary site, uses a dedicated Vast vector icon, and opens `chrome://vast/` with Chromium's normal tab-disposition rules. Its label and accessibility description follow only the validated active-workspace projection from the profile-keyed browser service; incognito and guest windows do not receive the control or normal-profile product state. The service now emits validated-status notifications after recovery, covered by the 24-test native data suite. A Windows UI Automation smoke test proves that the real native control is exposed, invokable, and reaches the Vast surface.

`0020-vast-workspace-selection.patch` turns the workspace projection into a safe interactive browser feature. Selection writes only an atomically replaced `VastProductData/workspace-selection.json` record below the Chromium profile, binds that record to the exact verified migration journal, ignores stale migrations, and never edits either the Electron source or committed `vast-data.json`. The profile-keyed service validates, persists, reloads, and broadcasts the effective workspace; typed Mojo makes the same operation available to the Vast workspace rail, while the native toolbar exposes checked radio items and a hub command on every regular website. The native suite is now 28/28, synthetic and supplied-backup WebUI tests prove persistence across a second browser restart, and Windows UI Automation verifies the real Views menu, private-workspace label, and restart recovery.

`0021-vast-native-workspace-tab-groups.patch` adds a browser-window-scoped `TabStripModelObserver` that maps validated Vast workspaces onto ordinary Chromium tab groups. Switching the existing native workspace menu expands and activates the selected group, collapses other Vast-owned groups, remembers the last active tab in memory, and assigns newly inserted unpinned/ungrouped tabs to the active workspace without persisting or exposing their URLs. Restored groups are reclaimed only by the exact Vast title convention; existing unrelated user groups are not renamed or claimed. Empty workspaces use a local placeholder document until the full workspace surface is ported. Windows UI Automation verifies two native groups, automatic assignment of a second Alpha tab, a crash-free Beta switch, source-data immutability, and restart-safe workspace selection. Exact cross-restart tab/group identity remains a later persistent-registry milestone rather than being inferred from user groups.

`0022-vast-workspace-group-registry.patch` adds the exact cross-restart identity boundary. `workspace-tab-groups.json` lives below the Chromium profile, contains only workspace IDs and canonical 128-bit Chromium tab-group tokens, is bounded to 64 KiB/128 entries, and is accepted only for the exact verified migration journal and known workspace set. The profile-keyed service serializes atomic read-modify-write updates from multiple windows; no tabs, URLs, titles, history, or product-file mutations enter the registry. The window controller loads registry state with generation ordering, prefers exact token matches, uses the `0021` title convention only to migrate pre-registry groups, assigns tabs that arrived before asynchronous recovery, and restores the real `chrome://vast/` workspace surface. The same patch fixes a non-insert observer `CHECK` by testing `TabStripModelChange::type()` before `GetInsert()` and fixes the WebUI's internal accessibility checker violation by giving the labelled settings container an explicit group role. Thirty-three native tests and Windows UI Automation cover malformed/stale/duplicate registry data, serialized updates, exact registered-token retention, named Alpha/Beta restoration, and absence of `unnamed group`/`Crashed` after a forced process restart.
