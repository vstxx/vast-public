# Vast 0.3.0–0.4.2 guest scrolling investigation

**Follow-up (2026-10-04):** The release-profile r5 runtime has since been built and measured with fixed-cadence synthetic input. See [guest-scroll-release-profile-followup.md](guest-scroll-release-profile-followup.md) for the current result and remaining acceptance work. The results below document the earlier testing-profile build and its less comparable serial-input method.

Status: **remediation incomplete**. The packaged 0.4.2 runtime still shows a synthetic SPA callback gap from 0.3.0. No result here establishes that Gmail or ChatGPT scrolling is fixed.

## Native build audit

`out/VastCompat/args.gn` imports `//electron/build/args/testing.gn` and sets `is_debug=false`, `symbol_level=1`, `use_remoteexec=false`. Its `gn args --list --short` output confirms `is_official_build=false`, `dcheck_always_on=true`, `chrome_pgo_phase=0`, `use_thin_lto=false`, and no V8 builtins profile. Generated Ninja compile commands contain `-DDCHECK_ALWAYS_ON=1`. This is direct evidence for how the approved binary was built, not merely documentation.

A separate `out/VastRelease` configuration imports `//electron/build/args/release.gn` with the same base revisions and source patch checkout. GN generation succeeded. Its `gn args --list --short` output confirms `is_official_build=true`, `dcheck_always_on=false`, `chrome_pgo_phase=2`, `use_thin_lto=true`, and `v8_builtins_profiling_log_file="//electron/build/pgo_profiles/electron-v8-builtins.profile"`. Its generated compile commands include `-flto=thin` and `-fprofile-use=../../electron/build/pgo_profiles/electron-win-x64-1788664530-949f5f529a.profdata`. These flags plausibly affect V8/Blink execution and rendering throughput; the benchmark has **not isolated their effect** from the custom native patches. An initial `-j 2` build was stopped after 226 of 46,607 Ninja steps. Its incremental `-j 8` continuation reached 7,368/46,381 before several `clang-cl` processes failed with `LLVM ERROR: out of memory`; no source compiler error was reported. The `-j 3` continuation reached 16,671/39,019 before Blink's bindings generator failed with Windows error 8 (`Not enough memory resources are available`). That generator internally starts a 24-process Python pool, so several concurrent Ninja actions exhausted available memory. Running the bindings group alone with `-j 1` succeeded. The resumed `-j 3` build reached 20,916/22,342 before simultaneous Clang compilation and ThinLTO linking failed with `LLVM ERROR: out of memory`. A `-j 1` retry failed on the first link target, `v8_context_snapshot_generator.exe`, because Chromium's Windows ThinLTO link flag was `/opt:lldltojobs=all` and still used all hardware threads. In the external Electron checkout only, `build/config/compiler/BUILD.gn` was changed to `/opt:lldltojobs=1` for this low-memory build; `gn gen` succeeded and `gn desc` confirmed the new linker flag while retaining PGO and ThinLTO. The release-profile build has been resumed with `-j 1`. This build-only change is separate from Vast's pinned r5 runtime patchset. No release-profile executable or performance result exists yet.

### Confirmed synthetic selector bottleneck

The SPA fixture updates rows every 50 ms with `document.querySelectorAll('.row:nth-child(50n)')`. With **identical ASAR file contents** and Electron/Chromium 44.3.0, six 30-sample DOM-only runs per runtime measured selector P50 at 0.1–0.2 ms on stock Electron and 19.7–42.0 ms on patched r5. A plain `.row` selector measured approximately 0–0.2 ms on both in a follow-up run. Updating styles and reading layout from the matched rows was also slower on r5 (roughly 2.7–5.8 ms versus 0.1–0.2 ms), but the positional selector dominated. The runs were interleaved stock/r5/r5/stock to limit changing background-load bias. They ran while a separate native build was active, so the absolute times should be repeated on an idle machine. A pure V8 Node-mode numeric/object-access probe on those binaries found comparable times, so this is not a demonstrated general JavaScript slowdown.

The source-level mechanism is explicit in pinned Chromium's `third_party/blink/renderer/core/dom/nth_index_cache.cc`: in the cached `NthChildIndex` branch, `DCHECK_EQ(result, UncachedNthChildIndex(...))` recomputes the answer. `UncachedNthChildIndex` walks every previous sibling. The approved r5 core compile flags include `DCHECK_ALWAYS_ON=1`, and `base/dcheck_is_on.h` makes `DCHECK_IS_ON()` true with that define even when `NDEBUG` is set. Thus the safety assertion makes repeated `:nth-child` matching on long sibling lists very expensive. The release-profile generated flags omit `DCHECK_ALWAYS_ON`, so this diagnostic recomputation will not be compiled into that candidate. This is a concrete explanation for the **synthetic SPA's** r5 script cost; it does not establish the actual Gmail/ChatGPT selector workload or whether another native patch adds cost elsewhere. The new binary and its speed still require a build and package test.

The r5 patchset includes network and extension lifecycle code (`0004`, `0005`, `0006`, `0007`, `0008`) and Blink CSS fallback fixes (`0009`, `0010`). The latter repaired reproduced renderer crashes and must remain in a production fix. Native `LOG(INFO)` diagnostics in extension/network paths are another possible cost, but were not measured during this benchmark. An r3 patched runtime, before the CSS fixes, exhibited the same synthetic SPA callback slowdown as r4 and r5. This rules out `0009` and `0010` as the cause of **this fixture's** slowdown; it does not prove their cost on authenticated sites.

## Benchmark method

Run `node scripts/guest-scroll-benchmark.cjs --executable=<packaged Vast.exe> --output=<new directory> --refresh-hz=144 --repetitions=3`. The harness starts a local HTTP server, a disposable Vast profile with one active webview, and a 1280×800 window. The observed guest viewport is 1280×673 at device pixel ratio 1. Windows reports a nominal 143/144 Hz display mode. Each repetition warms for 1.2 seconds, then dispatches 90 CDP `mouseWheel` commands to the **guest** target, awaiting each acknowledgment before an 18 ms pause. The fixtures are long text, a DOM-updating SPA, nested scrollers, and a virtualized list. Trace JSON and result JSON are saved under ignored `performance-results/`.

**Input timing limitation:** waiting for CDP acknowledgment does not produce equal event cadence across executables. `ScrollJankV4` arrival intervals on the first SPA run had a median of 31.7 ms in 0.3.0, 47.5 ms in 0.4.1, 46.9 ms in 0.4.2, and 31.3 ms in the stock 44.3.0 control. These are not equal-input-rate frame-pacing comparisons. The original schema-1/2 harness also included process inventory and trace retrieval in its rAF observation window. The revised harness brackets only scrolling and records actual arrival intervals and CDP round-trip time; its repeated measurements are not yet complete because some CDP dispatches timed out. Sending all 90 CDP wheel commands at a fixed 18 ms cadence caused Chromium to coalesce them (18 observed), and `Input.synthesizeScrollGesture` returned success without scrolling the webview. Those failed runs are excluded. This benchmark is useful diagnostic evidence, **not an acceptance-quality reproduction of physical wheel/touchpad scrolling**.

The primary `guestRafIntervals` measure **guest renderer animation callback cadence**. They are not display presentation intervals. `ScrollJankV4` and `Presentation` events supply input-related compositor evidence. `gpuDisplayIntervals` uses `Display::FrameDisplayed` events from the whole trace window, including host activity; it is not a pure guest frame sequence. The harness does not count missed monitor refreshes. Input was synthetic CDP mouse wheel, not a physical wheel or precision touchpad. The sites were isolated fixtures with no user extensions installed. Gmail and ChatGPT were not opened because they require interactive opt-in and a personal session.

All completed fixture repetitions scrolled to 9000 px and observed 90 wheel events and 90 scroll events. Chromium marked zero of 90 `ScrollJankV4` updates as janky in each repetition. That disagrees with treating the 20.8–20.9 ms rAF callback cadence as proof of visibly missed frames. The SPA's `gpuDisplayIntervals` P95 was about 48.7 ms on r3/r4/r5 and about 34.8 ms in the stock control, but those intervals mix host and guest output and sparse input. The virtualized callback gap remains even with stock 44.3.0, so it may involve the 0.4.2 app source or the Electron version difference. The synthetic results do not establish the user's real Gmail/ChatGPT symptom quantitatively.

The guest CDP `ScriptDuration` delta on the SPA was about 0.04 seconds per run with 0.3.0 and stock 44.3.0, versus 2.1–2.2 seconds with r5 0.4.2; `LayoutDuration` was about 0.07 versus 0.88–0.92 seconds. The older measurement window and slower r5 input acknowledgments make these *cumulative* totals unsuitable as normalized throughput figures. The number of layouts was about 113–123 versus 160–164, so count alone does not explain the time difference. These observations make the native runtime a strong candidate for the synthetic slowdown, but do not isolate GN flags from native patches. A trace of 90 wheel `EventDispatch` tasks yielded median durations of 0.037 ms (0.3.0), 0.110 ms (0.4.1), 0.098 ms (0.4.2), and 0.036 ms (stock 44.3.0). Wheel-listener overhead is measurable but too small by itself to account for the SPA script/layout gap.

The extension-disabled control uses Vast's internal compatibility rollback switch only in a disposable profile. That profile had no installed extensions, so it does not measure extension content-script costs. The GPU-disabled control selected ANGLE D3D11 WARP, with GPU compositing unavailable, and made all four fixtures worse. The hardware-backed control reported Intel UHD Graphics via ANGLE D3D11 with GPU compositing and rasterization enabled. Neither diagnostic configuration is proposed for production.

The stock control is **not** a viable production replacement: it lacks Vast's extension and CSS crash fixes. The r3/r4 controls likewise omit later required fixes. No production security feature was disabled.

## Source path and correction

The guest preload in 0.3.0 already had a non-passive wheel listener and similar overscroll logic. Version 0.4.2 removed the non-passive guest listener. Therefore that listener can explain part of 0.4.1's reported improvement but cannot by itself explain the full 0.3.0 to 0.4.1 regression. The current 0.4.2 guest listener is passive. Host `App.tsx` retains a non-passive Ctrl/Meta wheel handler for host UI zoom; webview events are excluded via the composed path. The guest does not use a custom smooth scrolling engine.

The preload correction in `src/preload/guest.ts` addresses three reproduced correctness faults: an inner list could falsely reveal Purist while its ancestor could scroll upward; a stale Purist reveal could survive a scroll boundary check with unchanged state; line-mode wheel deltas were treated as pixels. It also avoids potentially layout-dependent `scrollHeight` and `clientHeight` reads on each upward wheel event. Targeted VM tests exercise the actual transpiled preload. A strict pair of private 0.4.2 packages was built with the same runtime and metadata; comparing ASAR entries found only `out/preload/guest.js` different. After fixing the harness's initial-navigation race, both packages completed 3×4 fixture runs. Their SPA rAF P95 was 27.8–27.9 ms (parent) versus 27.8–28.0 ms (candidate), and both had zero `ScrollJankV4` janky updates. The text, nested, and virtualized rAF P95 also matched within rounding. This source change is a correctness fix, **not a performance remedy** for the main regression.

Other inspected path elements include `WebviewSurface.tsx` IPC handling and viewport resize, Purist `grid-template-rows`, `TabRetentionController.ts` background-throttling requests, main-process `setBackgroundThrottling`, and synchronous guest document-start IPC for spoofing, privacy, and extension rules. None is established as a new 0.4.x performance cause by the current measurements. The Purist grid animation can resize the webview while visible, but this fixture did not trigger it. Repeated background-throttling calls and document-start blocking remain audit candidates. Initial load, physical input, GPU backend, and extension-enabled profiles have not yet been measured to the requested acceptance standard.

### Packaged host UI baseline

After the native build stopped and before restarting it, `scripts/host-interaction-benchmark.cjs` measured the same private 0.4.2 parent and preload candidate packages in disposable local profiles. It clicks the real Settings and sidebar controls and measures DOM insertion plus two **host** rAF callbacks; these are not presentation timestamps. Cold Settings insertion took 322 ms (parent) and 321 ms (candidate); two-rAF times were 518 and 548 ms. Warm Settings insertion took 94–136 ms (parent) and 99–124 ms (candidate). Cold side-panel insertion took 317–318 ms; warm insertion took 9–17 ms. First Settings open produced 193–224 ms of observed long tasks; side-panel insertion had no observed long task. The candidate does not materially change these host paths. The cold/warm split points to lazy module load and first mount as candidates, while warm Settings still spends substantial time in rendering/style/layout. This is one 3-repetition session per package, so the absolute timings need independent repetitions before choosing an optimization. No Settings or sidebar product change has been retained from these measurements.

### Packaged guest load benchmark

`scripts/guest-load-benchmark.cjs` now drives local `Page.navigate` calls inside a packaged Vast guest, with a disposable profile, HTTP cache disabled, and no external sites. Its simple fixture makes no asset requests; its fanout fixture makes 48 same-origin CSS/JS requests, exercising the guest preload and session request hooks. It records guest Navigation Timing, FCP, long tasks, CDP observation latency, and the server's request count. Run it with `node scripts/guest-load-benchmark.cjs --executable=<packaged Vast.exe> --output=<new directory> --repetitions=3`. It does not measure real network latency, first GPU presentation, or the readiness of a real SPA. A one-repetition 0.4.2 run verified that navigation completed and all 48 asset requests arrived; it ran while the native build was active, so its times are **not** a performance baseline or a before/after result. Comparative package runs remain pending until the machine is idle.

## Compatibility and security risks

| Area | Evidence and risk |
| --- | --- |
| Native release profile | The proposed GN configuration preserves the pinned r5 patch checkout and omits the expensive `NthChildIndex` diagnostic recomputation. Turning off DCHECK changes assertion behavior, so CSS and extension tests must pass on the actual new binary; a successful GN generation alone establishes no binary safety or speed gain. The underlying CSS crash fixes remain required. |
| Blink CSS | Patch `0009` backports the upstream `env()` fallback handling; `0010` trims leading HTML whitespace in nested `var()` fallback substitution. Both execute in style resolution and preserve the authenticated-site crash fixes. r3's SPA slowdown predates them, but authenticated-site cost and release-profile behavior remain unmeasured. |
| ECE, webRequest and auth | Patches `0004`/`0005` add browser-process request, worker lifecycle, and auth routing, with `LOG(INFO)` diagnostics in some paths. The isolated SPA had no installed extensions; it cannot prove Bitwarden/Proton Pass behavior or rule out per-request overhead on those sites. Removing the hooks would risk auth, permissions, and extension function. |
| GPU | The hardware-backed ANGLE D3D11 run outperformed the WARP diagnostic control. The benchmark did not establish a faster safe backend; GPU or sandbox security switches should not be changed from this evidence. |
| Preload | The correction preserves a passive wheel observer and native scrolling. VM tests cover regular nested containers and stale Purist state. Shadow DOM and physical precision-touchpad behavior remain unverified; its matched private package comparison shows no synthetic speed gain. |

## Validation and remaining gates

The private candidate built with `npm run build` and was packaged with the approved r5 distribution using the internal unsigned electron-builder configuration. The benchmark directly launched its packaged `Vast.exe`; it did not substitute a development server. Targeted preload and benchmark helper tests and TypeScript typecheck passed. The full Node suite now includes the new CommonJS regression tests and passed 956 tests with one skip. A pre-existing `.env.release.example` previous-version mismatch (0.3.0 in that example versus 0.4.1 in `scripts/release-config.json`) was corrected to let that suite pass. Some earlier trace and CDP input runs timed out. A navigation-readiness fix let the strict private parent/candidate pair complete 3×4; the separately packaged historical versions still had occasional CDP timeouts, and missing fixture repetitions were rerun in fresh disposable profiles.

The existing `test:electron:css-env` gate timed out once while Ninja was reading the separate release-profile graph. After stopping that build, rerunning the same gate passed on the approved r5 binary: CSS `env()`/`var()`/Typed OM fallbacks resolved without leading whitespace or a renderer crash. `npm run test:extensions:e2e` passed restore, content script, storage, management UI, disable/enable, reload, Incognito isolation, restart persistence, and removal on the verified r5 runtime. `npm run test:adblock:extension-e2e` passed its local request, rule, cosmetic, lifecycle, and cache assertions; its logs nevertheless contained an Electron sandboxed renderer bundle error and an `Invalid guestInstanceId` exception during webview cleanup. Exit status alone should not be read as a clean renderer log. These tests do not validate an unbuilt release-profile candidate or personal password-manager sessions. The low-memory `-j 1` release-profile build is running; postbuild gates remain pending.

Before claiming the primary regression fixed: build the patched release-profile Electron from the pinned source, verify its exact binary/flags, run the CSS crash reproduction and extension/security gates, package it, and repeat the 0.3.0/0.4.2/candidate guest benchmarks at a comparable measured input rate. Then measure physical mouse and precision touchpad input plus actual Gmail/ChatGPT only with user opt-in. Loading, Settings, and sidebar require separate before/after timings. No public release has been created.
