# Transactional Chrome, Edge, and Firefox import for Vast 0.4.0

## Purpose and scope

Onboarding must show a truthful preview and persist nothing from another browser until the user confirms the final step. A failed or interrupted import must be retryable without duplicated bookmarks, inflated visit counts, partly installed extensions, or a false success screen. Existing Vast profiles and data must remain intact. Supported sources are Chrome, Edge, and Firefox; passwords, cookies, tokens, extension private storage, and additional browsers are out of scope. Firefox extensions are not imported.

This design replaces the renderer-owned import flow with a main-process import coordinator. It is divided into three implementation slices: (1) durable data transaction and bookmark/history model, (2) local Chromium extension transfer, and (3) onboarding/UI defaults and end-to-end validation. Each slice needs tests; none is a claim that 0.4.0 is ready to publish.

## Current failure modes verified in source

- `OnboardingPage.tsx` calls `importer.run` before final confirmation, merges into the live renderer store, and sets `importedKeyRef` after a failed result. Renderer autosave can persist that partial merge. `completeOnboarding()` precedes `storage.flush()` and a returned `{ ok: false }` is ignored.
- Bookmark import flattens Chromium root hierarchy, Firefox Places toolbar may become a user folder, and URL-only deduplication drops legitimate bookmarks. History merges sum `visitCount`; the importer reads 2,000 entries but the renderer keeps 1,000 and can overreport additions.
- SQLite files and WAL/SHM are copied separately; WAL copy errors are suppressed. Firefox bookmarks and history use different snapshots. Synchronous database and file work runs on Electron's main thread. Source path, row, depth, byte, and time limits are incomplete.
- Chromium extension detection is metadata-only. `installUnpacked` enables and loads immediately; it is not a consent-based import path. The managed installer has useful staging, validation, rollback, and channel checks but currently accepts only `.vext`, Hub, and the narrowly scoped Apple upstream package. Ordinary Manifest V2 is rejected regardless of actual runtime support.

## Coordinator and persistence contract

The main process owns one import session per Vast profile. Its bounded IPC API is `discover`, `prepare`, `preview`, `commit`, `status`, and `discard`; the renderer receives opaque session/operation tokens and summary data, never raw source paths. Discovery returns only allowed profile IDs and display names. It re-resolves and revalidates the selected source before every read; an IPC caller cannot supply an arbitrary path.

`prepare` locks source/profile/selected categories for the duration of a snapshot, runs bounded source readers in a worker thread, and produces a private, expiring preview. It does not mutate the Vast browser store or install/enable extensions. A single in-flight operation is enforced in main, not just by disabled buttons; repeated clicks and profile changes are rejected. Back/Next reuses the same valid preview. Changing source, categories, or profile explicitly discards it and its temporary files. Restart/Fresh start discards it and leaves previously persisted Vast data unchanged. A failed prepare releases the lock and remains retryable; no `importedKeyRef` remains as a success shortcut.

The preview reports, separately for bookmarks, history, and extensions: source counts; proposed additions, updates, duplicates/skips and limits; unavailable/failed conditions; extension permissions and compatibility warnings; and estimated serialized size. An unavailable category does not become `imported` because another category succeeded. If a selected category fails during prepare, the user must explicitly accept committing only the successful categories or retry; the selection is never silently narrowed. The final screen makes the chosen categories and pending extension consents explicit.

`commit` is the only operation allowed to write imported bookmarks/history. It serializes with all normal Vast storage writes, takes the latest persisted revision, merges without overwriting unrelated existing data, checks the 8 MiB limit on the complete serialized candidate, and writes one atomic candidate containing an operation receipt. A readback verifies bytes/revision before success is returned. Renderer autosave cannot race this write: storage writes carry a revision or are rejected/rebased while commit holds the lock, and the renderer is hydrated from the committed result. The previous data remains recoverable if write/readback fails. A failed `storage.flush()`/durability check is surfaced as failure, not success.

The operation ID and source/selection fingerprint are persisted with the committed data. If the write succeeded but the renderer lost the acknowledgement or Vast restarted, a retry reads the receipt and returns the same result without reapplying counts. If commit fails before the atomic rename, the retry starts from the last durable state. If the outcome cannot be established, main reports `indeterminate` and reconciles the file/receipt before permitting retry; it never blindly applies twice. Startup removes abandoned temporary snapshots/staged extension copies, but not a committed receipt. Back/Restart after a successful commit cannot undo data silently: the UI shows the committed status and offers an explicit new import flow, not a hidden rollback.

The commit receipt contains actual persisted `added`, `updated`, `skipped`, and `failed` counts per category. Extension installation results are separate post-commit receipts and never change the data transaction's success. Selected but unconsented extension transfer intents are persisted as source profile/extension IDs and fingerprints, without executable content being activated. If transfer is pending, the committed onboarding state is `extensions-pending`, not `completed`; restart routes back to consent. Temporary copied code is cleaned on restart, then re-copied and revalidated from the source before any resumed install. If the source vanished or changed, that extension becomes failed/retryable, never silently activated. Once every selected transfer is installed, declined, unsupported, or explicitly deferred, a separate verified storage write marks onboarding complete; failure leaves the resumable state. No source browsing data or extension payload is logged; operational logs include only category, counts, error code, and timing.

## Bookmarks and history

Bookmarks have stable Vast IDs and optional import provenance (`source browser`, `source profile ID`, `source item ID`). Identity is not URL-only. The store, bookmark toggle, menus, move/delete, persistence schema, and migration must operate on bookmark ID; same-URL bookmarks in different folders remain distinct. Reimport of the same source item is idempotent, while a user-created bookmark is never overwritten based only on its URL. The importer preserves Chrome/Edge Bookmarks Bar, Other, and Mobile roots as distinct Vast root mappings and preserves descendants within a bounded depth. Firefox resolves actual Places roots from `moz_bookmarks_roots`; it maps toolbar/menu/unfiled/mobile correctly and does not create a visible folder merely for the system toolbar root. Malformed cycles/depth overflow are reported and skipped, not recursively traversed forever.

History is limited by one consistent policy from query through store and persistence: at most 1,000 retained entries, ordered by valid last-visit timestamp (deterministic tie-breaker), with rejected/evicted items counted as skipped. Duplicate URLs merge using `max(existing.visitCount, imported.visitCount)`, never addition; last visit is the maximum valid timestamp. Firefox includes only URLs backed by actual `moz_historyvisits` rows and never converts zero visits to one. Chromium/Firefox timestamp conversion validates integer range, epoch units, NULL, and impossible values before ordering. Invalid records are skipped with counts. Existing Vast history is preserved according to the same cap and ordering policy; a preview that would evict an existing item must say so before consent. The 8 MiB preflight uses the candidate merged persisted payload, not only imported records, and fails clearly instead of silently truncating.

## Source discovery and SQLite safety

Chrome/Edge profile names come from bounded `Local State` profile metadata with a directory-name fallback. Firefox profiles come from bounded `profiles.ini`/install mappings, including permitted custom locations. Source paths are realpath-checked against the browser's discovered, user-approved profile roots; junctions and symlinks escaping those roots are rejected. No general filesystem path enters importer IPC. Standard and custom Firefox profiles are supported only where the configured path can be validated, not by scanning arbitrary disks.

An isolated worker performs source reads under file-size, row-count, directory-entry, tree-depth, total-byte, and wall-time budgets. Cancellation terminates the worker and removes its private temporary tree. For SQLite, use a read-only online backup into one temporary snapshot per source database, including active WAL state; run integrity/quick-check on the result. Firefox bookmarks and history query that same snapshot. Do not copy DB/WAL/SHM independently or ignore sidecar errors. A failed/inconsistent backup, locked source, corrupt database, exceeded budget, or source changed beyond a safe retry window produces a per-category error and Retry. No source database or profile file is edited. Temporary snapshots are owned by a dedicated Vast directory and cleaned on normal completion and next startup; cleanup is restricted to validated descendants of that directory.

## Chromium extension transfer

Chrome/Edge discovery reads bounded `Preferences` extension state and the matching `Extensions/<id>/<version>` directory. It reports source extension ID, manifest/version, enabled/disabled state, install location, and whether a usable directory exists; it does not open `Local Extension Settings`, IndexedDB, cookies, tokens, vaults, or other private extension data. Disabled source extensions remain disabled in Vast unless the user separately chooses to enable them. Firefox shows a clear “extensions cannot be imported from Firefox” explanation with no selector.

Prepare inventories only regular files within the canonical extension root, rejects symlinks/junctions/reparse-point escapes and unsafe paths, applies total/file/count/depth limits, and copies bytes to a private non-executable staging tree. It hashes the source inventory and the copy to detect concurrent source changes; any mismatch fails this extension with Retry. The original code and `manifest.json` are not rewritten or repackaged as `.vext`. Metadata about provenance/trust lives outside the copied extension directory. Staging is temporary and never runs an extension.

The manifest and referenced assets are validated on the staged copy and again on the permanent copy. Required/optional Chrome permissions, hosts, externally connectable surfaces, background, content scripts, CSP, and file paths are checked with the existing security policy plus targeted hardening. `vast` native capability declarations in an imported Chromium extension receive zero grants; the user cannot accidentally inherit Vast Native privileges from the source profile. Unknown or unsupported APIs do not automatically make a structurally safe package invalid. The preview names concrete limitations; a missing essential API can be `unsupported`, while a usable extension with known gaps can be `partial compatibility`. Security validation failures are `unsupported` or `failed`, never relabeled as partial merely to install.

Publisher authenticity is not inferred from a profile directory or `manifest.key`. Imported extensions are always labeled `Local / Unverified`, even if they carry a key, and never become `Official`, `Verified Publisher`, Hub-managed, or auto-updated. The source extension ID and installed runtime ID are recorded separately. When a valid manifest public key yields the same ID as the source profile and the stable copied runtime, preserve that ID; on any collision with an installed ID, show `already installed` and do not overwrite or change its update channel. If no such stable, matching ID can be established without modifying the extension, report `unsupported` for that extension in 0.4.0. Do not spoof an official ID or change the manifest to force it. This conservative rule can be revised only through a separate explicit identity design and tests.

At final onboarding confirmation, data commit completes first. Then each explicitly selected extension has its own permission-consent step and independent durable-copy/registry/load transaction. The approval must cover required Chrome APIs/hosts and clearly separate any optional permissions; the runtime grant boundary must enforce what was approved, not just display a dialog. Until consent, neither install nor load occurs. A decline leaves it uninstalled. A failed extension transaction rolls back only that extension's copy/registry/runtime and cannot roll back committed bookmarks/history or another successful extension. Duplicate/source-channel checks are repeated immediately before activation. The UI and receipt distinguish `installed`, `partial compatibility`, `unsupported`, `failed`, `already installed`, and `declined`. Known missing APIs are reported as limitations; unexercised paths are not claimed compatible. The local channel has no automatic Hub/CWS update association.

Ordinary MV2 is no longer rejected solely because it is MV2. The current special Vast network-provider rule remains protected: a locally imported manifest cannot acquire its privileged `vast_network`/document-rule behavior merely by declaring those fields. Imported MV2 is allowed only through the local Chromium channel after the same security/permission checks and a tested Electron/ECE capability matrix. Unsupported MV2 capabilities are reported per extension; there is no blanket MV2 enablement or relaxation of CSP, host access, native messaging, or webRequest policy. The rollout must include a real MV2 fixture E2E before calling the path supported.

## Onboarding and UI details

- All available Labs switches, including Spoofing, start selected for a **new** profile in onboarding. Existing profile values are preserved, each feature's own security gate remains, and network scanning does not start automatically.
- Clean Toolbar Icons defaults to ON for a newly created profile and for “Use defaults”; migration distinguishes an old missing setting from a new profile so existing users are not silently changed. Adblocker remains optional and is never auto-installed/enabled.
- New Tab plain text such as `avidae` or `onboarding` is a search query. The address bar keeps its current shortcuts, and explicit `vast://` URLs still navigate. Context-specific input resolution avoids changing address-bar semantics.
- Onboarding uses locally stored, license-reviewed browser/search logos, with textual fallback; no runtime external image fetch. Extension cards use actual Hub summary/description data where available, without implying a transferred local extension is Hub-verified.
- Settings left navigation receives one consistent readable text size, icon/text alignment, and spacing; this is a scoped CSS/accessibility pass, not a redesign.

## Verification and release gate

Tests must cover state-machine transitions; double click, Back/Next, profile switch, Fresh start, restart and lost acknowledgement; real storage failure and readback failure; existing-data preservation; bookmark duplicates/hierarchy; Firefox roots and actual visits; timestamp bounds; 1,000-history and 8 MiB limits; malicious paths/junctions; corrupt/locked/WAL databases and worker timeout; extension staging tamper, key/ID mismatch, collision, consent, rollback, MV2/MV3, missing APIs, and no private-data copy. Tests assert persisted files and runtime state, not source strings.

Electron E2E uses controlled Chrome/Edge/Firefox profiles in both closed and active-browser/WAL cases, verifies installed local extension startup and permission prompts, relaunches Vast, and checks idempotent receipts. Separate read-only checks of the user's actual Chrome/Edge/Firefox profiles require their presence and a safe test window; absent profiles or unavailable Firefox location are marked untested, never pass. Full unit/integration suite, lint, typecheck, extension E2E, and release/security regressions must pass on the pinned patched runtime. No full Electron rebuild is authorized without a reproduced source-level need. A final report lists exact changed files, commands/results, coverage gaps, and remaining compatibility limitations. Until these gates pass, this design is not release approval for 0.4.0.
